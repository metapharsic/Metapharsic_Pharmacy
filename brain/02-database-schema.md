# 02 — Database Schema

Purpose: the authoritative definition of every table, column, constraint, and index in the Metapharsic Pharmacy database, and the order in which they are created.

Target: PostgreSQL 16. Types below are PostgreSQL types. Laravel migration equivalents are
noted where the mapping is not obvious (`$table->decimal('total', 12, 2)` produces
`numeric(12,2)`; `$table->timestampTz()` produces `timestamptz`; `$table->id()` produces
`bigserial`/`bigint GENERATED BY DEFAULT AS IDENTITY`).

---

## 1. Naming and column conventions

| Convention | Rule | Example |
|---|---|---|
| Case | `snake_case` everywhere: tables, columns, indexes, constraints. No camelCase, no capitals. | `medicine_batches`, `quantity_available` |
| Table names | Plural nouns. Pivot tables are the two singular table names in alphabetical order. | `sales`, `sale_items`, `permission_role`, `role_user` |
| Primary key | `id`, `bigserial`, on every table including pivots. | `id bigserial PRIMARY KEY` |
| Foreign keys | `<singular_referenced_table>_id`, always `bigint`, always with a real FK constraint. Polymorphic pairs are `<name>_type` (`varchar(120)`, the model class) + `<name>_id` (`bigint`). | `medicine_id`, `medicine_batch_id`, `reference_type` + `reference_id` |
| Timestamps | `*_at`, always `timestamptz`. Never a bare `date` for a moment in time; never `datetime`. `created_at` / `updated_at` on every table (documented exceptions in §9). | `created_at`, `confirmed_at`, `last_login_at` |
| Calendar dates | Plain `date` only where the business means a day and not a moment. | `expiry_date`, `invoice_date`, `sale_date` |
| Booleans | `is_*` or `was_*`, `boolean NOT NULL` with an explicit default. Never nullable. | `is_active`, `is_prescription_required`, `was_successful` |
| Money | `numeric(12,2)`, always, with no unit suffix on the column name. Never `float`, `real`, `double precision`, or `money`. Nullable only where "not applicable" is genuinely different from zero; otherwise `NOT NULL DEFAULT 0`. | `total`, `discount`, `cost_price_at_sale`, `effective_cost` |
| Percentages | `numeric(5,2)`, expressed as a percentage (12.00 means 12 percent), never as a fraction. | `gst_rate`, `discount_percent` |
| Quantities | `integer`, signed. Signed because the ledger records negative movements. | `quantity`, `quantity_change`, `quantity_available` |
| Enumerated values | `varchar(n)` plus a `CHECK` listing the allowed values, mirrored by a PHP enum in `app/Enums`. No PostgreSQL `ENUM` type — adding a value to a PG enum inside a transaction is awkward and the CHECK is easier to evolve. | `status`, `type`, `mode`, `reason_code` |
| Free text | `text` for unbounded notes; `varchar(n)` where a length limit is meaningful (names, codes, references). | `note text`, `batch_no varchar(60)` |
| Structured blobs | `jsonb`, never `json`, never a serialised PHP string. | `old_values`, `new_values`, `settings.value` |
| Soft deletes | `deleted_at timestamptz NULL` on master data only. Never on transactional or ledger tables (§9). | `medicines.deleted_at` |
| Actor columns | `created_by` on every table that records money or stock; additional `confirmed_by`, `cancelled_by`, `approved_by`, `override_by` where the action is separately authorised. All FK to `users`. | `created_by bigint` |
| Constraint names | `<table>_<column(s)>_<type>`: `_pkey`, `_key` (unique), `_fkey`, `_check`, `_idx`. | `medicine_batches_medicine_id_batch_no_expiry_date_key` |

> **Cave law:** Money is `numeric(12,2)`. Never float. Ever. A float column in a migration is
> a blocking review comment, not a style preference.

## 2. Type decisions worth stating once

**Quantity is `integer`.** Every quantity column in v1 is a whole number of the medicine's
selling unit (strip, bottle, tube, vial, or tablet as configured per medicine on
`medicines.unit`). Splitting a strip to dispense half is handled today by defining a
tablet-level medicine, not by fractional quantity. The shop confirmed it never sells loose
units (Q-001, resolved) — `integer` is decided, not deferred, and no ADR beyond the money
notes in ADR-0004 is needed. No migration may introduce a fractional quantity column.

**Money is `numeric(12,2)`** — twelve digits total, two after the point, maximum
₹9,999,999,999.99. Per-unit derived costs (`effective_cost`, `cost_price_at_sale`) are also
`numeric(12,2)`, which means a per-tablet cost is rounded to the paisa. On very low-value,
high-count items this leaves a residue of a few paise per line between
`purchase_items.line_total` and `effective_cost × (quantity + free_quantity)`. That residue is
accepted, documented in `03-domain-rules.md`, and never silently redistributed. Raising the
per-unit scale is an ADR question, not a migration someone does quietly.

**Timestamps are `timestamptz`.** PostgreSQL stores UTC and converts on read; the application
timezone is `Asia/Kolkata` (`config/app.php`, day one — see trap 6). Report boundaries such as
"today" are computed in `Asia/Kolkata` and never with `CURRENT_DATE` in a query whose result
crosses a day boundary in UTC.

**GST rate is stored, not looked up at report time.** `gst_rate` is snapshotted onto
`purchase_items`, `medicine_batches`, `sale_items` and `return_items`. Slabs change; filed
returns must not.

Reading the core spine in words:

- A **medicine** is an idea and holds no stock. It has many **batches**.
- A **batch** is physical stock with one expiry date and one cost. It is created by exactly one
  **purchase_item** (or by an opening-stock adjustment), is consumed by many **sale_items**,
  and every change to its quantity — from any source — is one row in **stock_transactions**.
- A **sale_item** points at both the medicine and the specific batch it drew from. One printed
  line may be several `sale_items` when FEFO splits across batches.
- A **return_item** points at the original `sale_item` and puts stock back into that same batch,
  or into quarantine if it is not fit to resell.

> **Cave law:** Medicine holds no quantity, no expiry, no stock price. Those live on
> `medicine_batches`. A `quantity` column on `medicines` is a six-month bug with a head start.

**No `deleted_at`. No update path.** Cave law 8.

> **Cave law:** Sales are stone. No edit, no delete. Corrections are returns or cancellations
> that write reversing stock transactions. The only columns ever updated on a committed sale
> are `status`, `payment_status`, `paid`, `due`, and the cancellation columns — all of them
> through a Service, all of them audited.

## 9. Immutability, soft deletes and the two triggers

| Table group | Policy |
|---|---|
| Master data — `medicines`, `categories`, `manufacturers`, `customers`, `suppliers` | Soft delete (`deleted_at`). Rows are referenced by history and must remain resolvable. |
| Users | Never deleted, soft or hard. Deactivated via `is_active`. |
| Transactional — `sales`, `sale_items`, `payments`, `purchases` (confirmed), `returns`, `purchase_returns`, `stock_adjustments`, `expenses`, `customer_payments`, `supplier_payments` | **No delete at all, soft or hard.** Corrections are new, reversing rows. Draft purchases are the one exception: a draft has moved no stock and may be deleted outright. |
| Ledger — `stock_transactions`, `audit_logs` | **Append only.** No `updated_at`, no `deleted_at`. Protected by a `BEFORE UPDATE OR DELETE` trigger that raises an exception. This is the only business logic permitted to live in the database, and it is there because it is the guarantee everything else rests on. |
| Derived — `daily_sales_summary` | Freely truncated and rebuilt. Holds no truth of its own. |

The two triggers:

```sql
CREATE OR REPLACE FUNCTION forbid_mutation() RETURNS trigger AS $$
BEGIN
    RAISE EXCEPTION '% is append-only; % is not permitted', TG_TABLE_NAME, TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER stock_transactions_immutable
    BEFORE UPDATE OR DELETE ON stock_transactions
    FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

CREATE TRIGGER audit_logs_immutable
    BEFORE UPDATE OR DELETE ON audit_logs
    FOR EACH ROW EXECUTE FUNCTION forbid_mutation();
```

## 10. Invoice numbering

### The format

```
PHARM / 26-27 / 00042
  │       │        └── last_number, zero-padded to `padding` (5)
  │       └── financial year, Indian: 1 April 2026 – 31 March 2027
  └── series prefix, from `invoice_counters.prefix`
```

Series in use: `PHARM` (sales invoices), `RET` (credit notes / sales returns), `PRET` (debit
notes / purchase returns), `ADJ` (stock adjustments). Each has its own counter row per
financial year, so the sales series is unbroken even if a return fails.

### The counter table

One row per `(series, financial_year)`, unique-constrained. The row is created on first use of
that year by an upsert, so no April-1st ceremony is required:

```sql
INSERT INTO invoice_counters (series, financial_year, prefix, last_number, padding,
                              created_at, updated_at)
VALUES ('PHARM', '26-27', 'PHARM', 0, 5, now(), now())
ON CONFLICT (series, financial_year) DO NOTHING;
```

### The locked read-and-increment

Issuing a number is a single statement. `UPDATE` takes a row-level exclusive lock, and
`RETURNING` hands back the value the winner produced — no separate read, and no window in which
two transactions can see the same `last_number`:

```sql
UPDATE invoice_counters
   SET last_number = last_number + 1,
       updated_at  = now()
 WHERE series = 'PHARM'
   AND financial_year = '26-27'
RETURNING prefix, financial_year, last_number, padding;
```

A second transaction running the same statement concurrently blocks on the row lock until the
first commits or rolls back, then re-reads the committed value and increments from there. The
number is then formatted in PHP:

```
sprintf('%s/%s/%0'.$padding.'d', $prefix, $financialYear, $lastNumber)
```

Rules that go with it:

1. **The financial year comes from `sales.sale_date`, never from `now()`.** A back-dated entry
   made on 2 April for a 31 March sale belongs to the previous year's series.
2. **The increment is the last write before `COMMIT`.** The counter row is the hottest row in
   the database at 11am; hold it for microseconds, not for the duration of stock allocation.
3. **A rolled-back transaction gives the number back.** Because the increment is part of the
   sale's transaction, a rollback un-does it and no gap appears. This is the reason the counter
   is a table row and not a PostgreSQL `SEQUENCE`: sequences are deliberately non-transactional
   and `nextval` is not rolled back, which produces gaps in a legally numbered series.
4. **`sales.invoice_no` still carries a UNIQUE constraint.** Belt and braces. If it ever fires,
   something has bypassed `InvoiceService`.

> **Cave law:** An invoice number is issued by a locked read-and-increment on
> `invoice_counters`, and by nothing else.

### Why `count() + 1` is forbidden

```php
// FORBIDDEN. Do not write this. Do not "temporarily" write this.
$next = Sale::whereYear('sale_date', $fy)->count() + 1;
```

Four independent reasons, any one of which is fatal:

1. **It is not atomic.** Under PostgreSQL's default READ COMMITTED isolation, two concurrent
   sales both count the committed rows — neither sees the other's uncommitted insert — and both
   compute the same next number. One commits; the other violates the unique constraint and the
   cashier sees an error mid-bill, in front of a customer, at the busiest hour. Without the
   unique constraint it is worse: two invoices share a number and the GST return is wrong.
2. **Deletions and cancellations move it.** A cancelled sale still occupies a number. If
   `count()` is the source, cancelling one bill makes the *next* bill reuse a number already
   printed and handed to a customer.
3. **It cannot express a series or a financial year cleanly.** The count would need filtering by
   series and year, and every such filter is another chance to disagree with what was printed.
4. **It gets slower every day.** A count over a growing table sits in the critical path of every
   sale, for a value a single indexed row could have given in constant time.

The same reasoning bans `MAX(invoice_no) + 1`, which has all of the same race conditions plus
string parsing.

## 11. Deliberate deviations from the Part 0 rules

Recorded here so they are decisions, not drift.

| Deviation | Where | Rationale |
|---|---|---|
| No `updated_at` on `stock_transactions`, `audit_logs` | §4.6, §4.7 | The rows are immutable and trigger-protected; an `updated_at` column would imply an update path exists |
| No `units` lookup table | `medicines.unit` is a CHECK-constrained `varchar(20)` | The unit list is short, stable, and referenced in code. A lookup table would add a join to the POS search path for no behavioural gain. Revisit if the shop ever needs unit conversions. |
| `users.role_id` alongside the `role_user` pivot | §4.1 | `role_id` is the *primary* role, used for defaults and the cost-visibility scope; `role_user` is the authoritative permission set. Kept consistent by an observer. |
